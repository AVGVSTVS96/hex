# T3 Code

A channel that serves the agent to [T3 Code](https://github.com/pingdotgg/t3code) as an [ACP](https://agentclientprotocol.com) agent. Pick it in T3's agent picker, in any project, and that T3 thread is its own Claude Code session working in that project, run by the hub like every Telegram topic or Buzz thread. Its intent, invariants and design live in the old fork's [`t3-acp/PATCH.md`](https://github.com/AVGVSTVS96/claude-plugins-official/blob/989adf98ed3ebfeb225b27635853be59d62b0b1f/patches/t3-acp/PATCH.md).

- `bot.ts` runs in the hub service (`bun hub/serve.ts`) next to Telegram, Discord and Buzz. It embeds the hub and serves ACP on `acp.sock`: `session/new` opens a thread in the request's `cwd`, kept only once its first `session/prompt` arrives (T3's provider check opens sessions it never prompts), `session/prompt` delivers the message and streams the turn back, `session/cancel` or T3 quitting mid-turn stops it, `session/resume` picks a thread up again after T3 restarts, and `session/set_config_option` sets the thread's model and effort from T3's pickers.
- It's also a client of the hub like the other apps, so `handoff` and `mirror` bring a thread from Telegram, Discord or Buzz into T3. `place` opens a thread in the T3 project of the session's folder and has T3 import it as one of hex's sessions, through T3's own server (`t3code.ts`: a short-lived token from T3's CLI, revoked after, and its WebSocket RPC). T3 shows only what an agent says on its turns, so `backfill` sends the chat in as turns: each of the owner's messages goes to the thread, and its recorded replies answer it as it comes back, without Claude. The session resumes with the first message the owner sends there. `session/list` and `session/load` answer for these threads, so T3 can find and open them again.
- `transcript.ts` turns a session's Claude Code transcript into ACP `session/update` notifications: text, thinking, tool calls and their results. A turn ends when the session's work does: background agents keep it open, and the turns their results start stream into it, until a Stop hook reports no background agent still working.
- `channel.ts` is the channel the hub serves each session over HTTP (`.mcp.json`). It only delivers T3's messages: the session's own output is what T3 shows, so it has no reply tool.
- `acp.ts` is what T3 starts. It relays stdio to `acp.sock`, so T3 reaches the agent that's already running instead of starting one. A hub restart closes the socket, so it connects again and opens the new hub the way T3 opened the old one (`initialize`, then `session/resume` for each session and `session/set_config_option` for what T3 picked in it), and asks again what T3 still waits on: a prompt becomes `_hex/rejoin`, which streams its turn again from when T3 sent it, with the updates T3 already has dropped (a prompt its session hadn't taken yet is still in `state/hex.db`, which gives it to the session like any message); a `session/load` sends the thread's history again, which keeps its message ids, with what T3 already has of it dropped the same way. T3 never sees the restart.

State lives in `~/.claude/channels/hex/t3/` (or `T3_STATE_DIR`): `threads.json`, `placed.json` (the threads hex opened in T3), the sockets, and `inbox/`, where pasted images and files land for the session to read.

Add the agent in T3 Code's settings as a local ACP agent whose command is `bun acp.ts <state dir>/acp.sock`. hex does it with `hex acp`.
