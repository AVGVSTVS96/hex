# Working on hex

This repo is hex itself, changed in a clone of its own and landed by pull request, since every installed hex updates from `main`. A user's hex is their own folder (`~/hex`) with this repo cloned inside as `.hex/`; their sessions run in that folder, never in here. Nothing personal goes in this repo: no names, accounts, machines or memories.

- `HEX.md` is how the assistant works, read in every user's every session: a line belongs there when any hex needs it and nothing in it is one user's. Each user's `AGENTS.md` imports it, so write it to the assistant, in the user's voice.
- `defaults/` seeds a new user's folder (`bin/hex init`); updates don't copy it again (changing a seeded file takes `bin/migrate`), so anything every hex must get belongs in `HEX.md`, `plugin/` or `bin/`.
- `plugin/hooks/hooks.json` lists what runs in every session: what a compaction's summary keeps (`bin/precompact`) and the last turns after it, or for a new session taking over a thread whose cache expired (`bin/compacted`), what's typed in a terminal and each turn's last words, into hex.db's message log, with the turn then queued for the memory agent (`hub/state.ts`), open tasks and questions (`hub/tasks.ts`), rule changes mid-session, and hex updates to what a session loads only at start (`bin/rules`), and a quick check of every brief or message that hands the owner's work to another agent, rewrites included, against their words, rules and memory (`hub/intent.ts`, logged to `state/intent.jsonl`). The memory agent (`hub/observe.ts`) writes every note, its compressions and the profile, commits the notes in the owner's folder, and has `bin/wake` rewrite `state/wake/CLAUDE.md`: the profile and memory ([OptMem](https://github.com/VictorTaelin/OptMem), downloaded by `bin/optmem`, never committed) that `HEX.md` imports, so every session loads them at start and after compaction.
- `hub/` gives every thread its own session (`bin/session` starts it, loading its instruction files and the wake from a copy that's taken again only as it compacts, so a resume doesn't send them again: `bin/instructions hold`; each prompt brings it the memory notes written since, `bin/rules`), retries a failed compaction, and carries on a turn the API refused, once another turn goes through, and keeps every message, task and question in `state/hex.db` (`hub/store.ts`, one file per domain in `hub/store/`). A hold puts threads on hold for every session to see, ends at its time or by `hex hold end`, and wakes the threads it frees, two at a time (`hub/holds.ts`). A `schedules.json` job fires as a prompt to its thread, or, when it names an idea or says `check`, runs as a quick check in its own session that wakes the thread only with news (`hub/schedule.ts`, `hub/ideas.ts`, logged to `state/ideas.jsonl` and `state/checks.jsonl`). A DM's session, once spent, gives way to a fresh one that sees the chat as an [OptChat](https://gist.github.com/VictorTaelin/91837951a5ce5b38f341ec1ba1df6449) tree (`bin/chat`). `channels/` holds the clients: Telegram, Discord, Buzz, T3 Code, voice, and iikb, which shows the owner's Telegram as chats in a keyboard and so has no sessions or `.mcp.json` of its own. Each reaches the hub only through `@hex/hub` (`hub/index.ts`), since its `tsconfig.json` roots it in its own folder, so a path into `hub/` fails `tsc`. Telegram and Discord began as [Anthropic's](https://github.com/anthropics/claude-plugins-official) and no longer follow it, so port an upstream fix by hand and run `bin/check` ([the old fork](https://github.com/AVGVSTVS96/claude-plugins-official) has each change's intent in a `PATCH.md`).
- `bin/job` runs long work as its own systemd unit that wakes its thread when it ends; a `claude` job runs as a hex session in the folder it was started from, without the wake, so it and the agents it starts work from the prompt, and `bin/session` trusts the folder a background session starts in. `bin/update` ships hex only after `bin/check` passes and once no hex session is busy (`bin/quiet`).
- `computer/` sets up hex's own Fly.io Sprite, `bin/vault` is [enclave](https://github.com/AVGVSTVS96/enclave) plus typing on that computer (enclave owns the relay, page and store, so changes to them go there), and `media/` makes videos in `site/`'s look, keeping its colors and app mocks (`media/kit/apps.css`) in step with `site/style.css`.

`bun run check` (oxlint, oxfmt, then `bin/check`: tsc, builds and tests) gates every pull request in CI; `bun run fix` fixes what it can. Tool arguments, socket lines and stored rows are zod schemas, parsed where they come in (`tool()` and `dispatch()` in `hub/mcp.ts`).

[CONTRIBUTING.md](CONTRIBUTING.md) has the pull request flow.
